# 中文润色与第一人称

写的是个人博客，读者点进来是想看**一个人**怎么想、怎么做的，不是看一份产品手册，也不是读散文。这篇讲两件事：怎么让中文读起来像人写的，以及「我」该出现在哪里。

写法参考了 [op7418/Humanizer-zh](https://github.com/op7418/Humanizer-zh)（MIT，© 2026 歸藏），按本博客的类别裁剪并改写。

---

## 两条优先级高于文风

**一、不编经历。** 第一人称的前提是那个第一人称真的做过这件事。用户没说的，不要补：几点开始做的、试了几次、花了多久、当时什么心情、有没有笑出声。缺素材就问，或者只写判断、不写故事。「我在这上面耗了一整天」如果没人说过，就是编的。

**二、不改事实。** 润色时最容易顺手改掉的是限定词。「可能」改成「会」，「计划」改成「已经」，「部分场景有效」改成「有效」。这些词承载的是证据强度，不是语气。原文说没验证过，改写后也得说没验证过。

这两条比下面所有条目都重要。文风是最后一步，不是第一步。

## 第一人称怎么用

### 用「我」，不用「本站」「我们」

个人博客只有一个作者。默认主语是「我」：

- 好的：我最后选了手动发布，因为自动构建每次都要等六分钟。
- 差的：本项目采用手动发布方案，以降低构建等待时间。
- 也差：我们采用了手动发布方案。（除非真的有人在跟你一起做）

### 第一人称放进具体的动作和判断里

「我」不是每段开头的装饰。它最适合出现在三个位置：

| 位置 | 写什么 | 例子 |
| --- | --- | --- |
| 做过的动作 | 具体到能被人复现 | 我把 `deploy:pages` 拆成了两步，先本地 `generate` 再上传 |
| 当时的判断 | 带理由，允许不确定 | 我一开始以为要改 router，后来发现 `/api` 本来就在转发列表里 |
| 真实的取舍 | 承认代价 | 这个方案省了钱，代价是每次发文章都得自己点一下重构 |

不适合出现的：版本号、别人的库怎么工作、客观事实。「我认为 Vue 3 的 `defineProps` 是编译期宏」——这不是观点，是事实，去掉「我认为」。

### 别表演情绪

第一人称最常见的假，不是编了某件事，而是给真实的事编了反应。

> ✗ 笼子落地、丝线绷断，我几乎是笑着按下开始键。
> ✓ 开局那段过场我看了两遍。

「看得入迷」「笑出声」「心头一暖」「久久不能平静」——这些如果是真的，写；如果是为了让句子好听加上去的，删。判断句比情绪句耐读，也更像你自己的话。

### 一段一个「我」就够了

「我试了…我觉得…我发现…我最后…」堆在一起，读起来像流水账，也像在证明自己真的在场。把动作合并，把「我」留给真正有判断的地方：

> 改写前：我先打开了 wrangler.toml，我看到了 `[vars]`，我觉得这里可以加，然后我加上了。
>
> 改写后：`[vars]` 里本来就有位置，直接加了两行。

### 按类别调人称

| 类别 | 第一人称的用法 |
| --- | --- |
| `study` 学习笔记 | 过程用「我」讲（我踩了这个坑，我试了两条路），结论回到客观陈述。读者要的是可复现，不是你的心路历程 |
| `game` 评测 | 全篇「我」。主观就是这类文章的价值，别写成评分说明书 |
| `work` 作品 | 全篇「我」。作者就是作者，用「本工具」「该项目」反而疏远 |
| `resource` 资源 | 「我」只用来交代用途（我用它做什么），不用来夸（我觉得它超级好用）。夸要用具体场景替代 |
| `other` 随笔 | 全篇「我」，允许犹豫、跑题、没有结论 |

## 先管住抒情

这是中文 AI 最明显的痕迹，也是最容易被当成「文笔好」放过去的。**个人博客不需要文学性，需要具体。**

### 抒情的替代品是判断

删掉一句抒情之后，位置会空着。填进去的应该是判断，不是另一句抒情：

> ✗ 手动发布像一种仪式，把「写完了」和「发出去了」之间那道缝重新撑开。
> ✓ 手动发布多花几分钟，但这几分钟里我会再扫一遍正文。代价是慢，好处是发出去的版本我确实看过。

判断的特征：可以被反对，能说出理由，指向具体的东西。「这是一次远行」没法被反对，也没有理由，所以它不承载信息。

不确定的也写出来。「这条我还没想明白」「先这样，等下次踩坑再说」比一个漂亮的结论更有用，也更像人在写。**参差不是把话说干，是允许有些地方没结论。**

### 1. 金句额度

一篇最多留一到两句能被单独摘出来的句子，其余地方把话说清楚。

> ✗ 免费套餐的限制是真的，但它教会我一件事：便宜不等于无代价，只是代价换了地方——从账单换成了注意力。
> ✓ 免费套餐够用，只是每次发文章要自己按一下。

金句的问题不是它假，而是它挤掉了本来说得清的那句话。写到「这件事让我明白」的时候，先问：明白的是什么具体的东西？

### 2. 比喻要落回事实

一个比喻换来的是理解，不是气氛。用完必须能接回具体的事。

> ✗ 按下按钮之后，页面要等几分钟才变，这几分钟里我会去刷新、会去确认，像寄出一封信后守在门口。
> ✓ 按下按钮后要等几分钟，我会刷新两三次确认页面真的变了。

「像…」「仿佛…」「宛如…」一段出现两次以上，基本就是在拿意象顶替描述。

### 3. 意义拔高

> ✗ 上线手动发布，标志着部署流程进入了新阶段。
> ✓ 上线了手动发布。自动构建仍然关着。

「标志着」「开启了新篇章」「具有里程碑意义」后面通常什么都没有。删掉升华句，保留事实。

### 4. 句尾升华

> ✗ 页面支持全文搜索，充分彰显了对用户体验的不懈追求。
> ✓ 页面支持全文搜索，方便找术语原文。

「彰显了」「体现了」「展现了」经常只是给前一句加尾巴。有真实的原因和目的才留。

### 5. 格言式伪深度

> ✗ 部署，是一门关于耐心的艺术。而且它高得诚实。
> ✓ 部署慢，主要是等构建。难度偏高，但每次失败都能看出是哪一招没接住。

短促的、下定义的、听起来像结论的句子，如果没有增加理解就不要用。真要用，后面得能落到具体的事上。

### 6. 宣传语

> ✗ 这套方案稳定可靠、快速响应、易于维护，堪称个人博客的最优解。
> ✓ 这套方案每月跑一次同步，出错时页面显示上次成功的快照。

没有数据就别写形容词。有数据就把数据写出来。主观评价可以留，但要让它看起来像评价，而不是结论。

## 再删铺垫

### 7. 预告式开场

> ✗ 接下来，让我们深入看看 Cloudflare 的部署流程。
> ✓ Cloudflare 的部署流程分四步。

「本文将带你了解」「下面我们一起来看」这类句子删掉，正文直接开始。不要拿新内容填删掉的字数。

### 8. 「随着…的发展」

> ✗ 在技术不断发展的时代背景下，静态站点生成方案层出不穷。
> ✓ 静态站点生成这两年多了不少选择。

只有背景本身带信息（有趋势、有时间、有因果）时才留。纯垫场就删。

### 9. 首句复读标题

> ✗ ## 部署顺序 / 本节介绍部署顺序。
> ✓ ## 部署顺序 / 顺序是先迁移再部署 Worker，反过来会缺表。

标题下面的第一句要往前推一步，不是把标题再说一遍。

## 然后看句子

### 10. 「不仅…更是…」

> ✗ 这不仅是一个部署脚本，更是对工程效率的全新诠释。
> ✓ 这个脚本把四步打包成一条命令。

两部分都在提供信息时才留。只为抬高语气的假对比，删掉否定那半边。

### 11. 三段式排比

> ✗ 这次改版带来了性能、体验与可维护性的全面提升。
> ✓ 这次改版把首屏 JS 从 480 KB 降到 210 KB，列表页多了搜索框。

三个名词并列很顺口，但常常三个都没说清。逐个检查：每项有独立信息吗？没有就换成具体数字或动作。**不要为了凑数补第四项。**

### 12. 破折号当万能连接

> ✗ 结果出来了——路由没生效——原来配置写错了。
> ✓ 结果是路由没生效，原因是配置写错了。

解释、插入、转折是真的才用破折号。一段里出现两三次，多半是在拿停顿冒充节奏。

### 13. 短句碎片成串

> ✗ 构建失败了。很彻底。整个流程卡住了。
> ✓ 构建失败了，整个流程卡在第二步。

连着的碎句要么承载新事实，要么是刻意的强调。否则合并。

### 14. 限定词堆叠

> ✗ 这个调整也许可能会在某些情况下略微改善加载速度，但目前尚未验证。
> ✓ 这个调整可能改善加载速度，还没验证。

一层不确定性用一次就够了。「也许可能」不是更严谨，是更含糊。

### 15. 被动和缺主语

> ✗ 该配置被进行了优化，性能得到了提升。
> ✓ 我把缓存头改成了 `max-age=31536000`，重复访问省掉了整次请求。

施事者是你自己、说清楚更省事时，改主动。施事者真不知道（「样本已被污染」）就保持被动，也别编一个「系统」出来。

## 最后是词

### 16. AI 高频词

> ✗ 本文将深入探讨如何赋能部署流程，打造无缝闭环。
> ✓ 本文讲怎么把四步部署合成一步。

`赋能`、`闭环`、`无缝`、`深入探讨`、`至关重要`、`全方位`、`一站式`——这些词在技术文里几乎总可以换成具体动作，或者直接删掉。但在它们真的准确的地方（闭环反馈、无缝迁移）不要动。

### 17. 借权威

> ✗ 业内专家普遍认为，静态生成是博客的最佳选择。
> ✓ 官方文档推荐静态生成用于内容为主的站点。

「专家认为」「研究表明」没有出处时，要么补出处，要么删掉这层背书，只留你自己的判断。**不要自己造一个机构名或日期。**

### 18. 套话收尾

> ✗ 总而言之，让我们拭目以待，期待更多精彩。
> ✓ 下一步是给同步加个失败告警，还没做。

结尾写下一步、写遗憾、写具体感受都行，别写祝愿。

### 19. 客服腔

> ✗ 希望这篇文章对你有帮助！如果还有问题，欢迎随时留言交流～
> ✓ （直接结束，或者写一句真实的话：这个坑我踩了两次才记住。）

「好问题！」「让我们开始吧」「希望对你有帮助」是对话残留，正文里没信息。

## 排版和中文句式

### 20. 粗体当装饰

一段里两三个加粗关键词，等于没有重点。加粗留给「扫一眼就要看到的操作」：破坏性命令、必填参数、警告里的后果。

### 21. 四字词、「的」和「进行」

- 四字排比：「稳定可靠、快速响应、易于维护」→「运行稳定，响应快，也方便改」。拆开写成具体的话，不补数据。
- 层叠的「的」：「这是一个十亿参数的开源小模型的微调的完整方案」→「这套微调方案适用于一个十亿参数的开源小模型」。
- 「进行+动词」：「对系统进行全面测试」→「全面测试系统」。
- 标点：正文用中文引号「」或「“”」，不要中英混排的直引号；代码块、URL、JSON 里的原样保留。

## 比单个词更像机器的东西

上面每一条都能被列举，所以也都能被猜出来。真正露馅的是整篇的**均匀感**：

- 每段都以主题句开头，段尾再小结一句
- 所有段落长度差不多，都是三到五行
- 每个小节都是同样的结构：定义、优点、缺点、总结
- 每篇结尾都要升华一次
- 通篇没有一句多余的话，也没有一句没想清楚的话

人写东西不会这么整齐。允许一段只有一句话；允许某段直接跳到结论；允许写「这条我没搞明白」；允许把最想说的那句放在最后，而不是在开头总结出来。

**一句话原则：宁可写得参差，不要写得均匀。**

## 写完自查

- [ ] 通篇主语是「我」，没有「本站」「我们」（除非真有人一起做）
- [ ] 每个「我」后面跟的是真实做过的动作或判断，没有编出来的时间、次数、心情
- [ ] 删掉所有「本文将」「接下来」「总而言之」之后，文章还成立
- [ ] 全文的比喻和金句加起来不超过三处，且每处后面都落回了具体的事
- [ ] 每个形容词旁边能找到对应的数字、现象或场景
- [ ] 段落长度不一致；至少有一段不是三段式
- [ ] 限定词和原文一致：没验证的还是没验证，可能还是可能
- [ ] 没有为了「去 AI 味」把术语、版本号、代码标识符改掉

自查不是打分。不要用「像不像 AI」代替「说得对不对」。
