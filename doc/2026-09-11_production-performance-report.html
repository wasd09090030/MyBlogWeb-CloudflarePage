二、关键发现（按影响排序）

  1. 【最严重】文章详情页封面图走 302 跳到 630 KB 原图，单图决定整页 LCP。 文章页 LCP 元素是 IMG.w-full.h-full（面积 470400 px²）， 它直接引用 /images/i_tvrehtqGZco89Q6Q。实测该 URL 返回 302 → cfimg.wasd09090030.top/file/gallery/…webp（630 KB）， 意味着一次额外跳转 + 一次到图片域的 TLS 握手，最终下载一张未按展示尺寸裁剪的原图。 同一资源的缩略图变体 /images/thumb/card/i_tvrehtqGZco89Q6Q.webp 仅 49 KB（直出 200，无跳转）， 体积相差约 12.9 倍。
    轨迹显示该请求 t+951 ms 发起、耗时 6.35 s 才结束， 而 LCP 记录 loadTime 7304 ms、 renderTime 7340 ms， 与页面 load 事件（7304 ms）几乎同时 —— 即整页的 LCP 与 load 都在等这一张图。 代码层根因在 features/article-detail/components/CoverImage.vue： coverImageUrl || thumbnailUrl 的优先级让「原生大图」永远压过「缩略图」。
  2. LCP 底图的「图片已就绪」与「实际绘制」之间有 2711 ms（桌面）/ 4955 ms（移动）的空窗。 LCP 候选的完整时序是：imageDiscoveryTime 1838 → imageLoadStart 2018 → imageLoadEnd 2717 → renderTime 5428 ms。 对照同页一个普通 <img>（loading.gif）的对应值为 866 → 2252 → 2780， 即普通图片在加载完成后约 528 ms 就完成绘制， 而 .hero-girl 这一 CSS mask 元素要多等数秒。 该元素带 will-change: transform 与无限 hero-girl-float 动画（合成层）， 推测其绘制被推迟到后续某次主线程重绘帧。 这一项需在 preload 修复后复测确认是否随之消失，因此本报告把它列为待验证的次生现象。
  3. 首张 LCP 候选其实是「加载中」占位 GIF。 首页 LCP 候选序列为：先 loading.gif（桌面 t+2777 ms，面积 20033 px²）， 后 .hero-girl（t+5427 ms）。 也就是说在 hero 剪影绘制出来之前，页面献给 LCP 的最大内容块是一个 58 KB 的占位动图—— 它既拖慢网络（移动端 Slow 4G 下 5.6 s），又占着首屏最大绘制面积。
  4. 关键资源的缓存策略不一致，两个「非哈希、首屏必需」的资源反而是最短缓存。 实测响应头：/hero/girl-full-silhouette.webp 为 Cache-Control: public, max-age=0, must-revalidate（每次访问都要发条件请求）， /fonts/open-sans-400.woff2 同样为 max-age=0, must-revalidate； 而 /_nuxt/*、/icon/logo.webp、/flower/*.webp、 /Picture/loading.gif、/images/thumb/* 都是 max-age=31536000, immutable。 hero 图恰好是 LCP 底图，却要每次重新验证，是可直接消除的一次往返。
  5. 占位图被当成文章配图写进了 sitemap。 sitemap.xml 共 312 条 image:loc，其中 74 条指向 /Picture/loading.gif。 搜索引擎会把「加载中」动图当作这些页面的代表性图片，属于可避免的 SEO 缺陷。 根因同上：占位图被服务端渲染进了页面 HTML，被 sitemap 模块自动采集。
  6. 文章页 CLS 0.0788 有明确可定位的来源。 位移集中在 t+6041 / 7309 / 7557 / 9057 / 10608 ms 五处（合计约 0.053，占总量的 68%）。 其中 t+7309 ms 一次位移的来源是 DIV,SPAN,SPAN,SPAN,BUTTON， 与封面图加载完成时刻（7340 ms）吻合 —— 根因是 CoverImage.vue 先以固定 aspect-ratio: 1.5 渲染容器，图片 onload 后再用 Math.max(imageRatio, 1.5) 改写比例，容器高度在收到图片后发生变化，必然产生位移。 其余四处来源为空（""），发生在水合与异步内容插入之后，需要在真实浏览器里逐个复现定位。
  7. TTFB 高企 624–663 ms，是整条链路的起点损耗。 HTML 首字节在桌面与移动端几乎一致（663 / 624 ms）， 说明它与设备无关，属于网络往返 + 边缘节点分发成本。所有子资源要等到 669 ms 才开始请求，也就是 FCP 之前已有约 0.67 s 纯粹消耗在"等 HTML"上 （占桌面 FCP 的 25%，占桌面 LCP 的 12%）。 站点经 Cloudflare 分发，这段延迟与访客到边缘节点的物理距离直接相关； 若主要访客在中国大陆，值得实测确认是否存在就近节点缺失导致的绕行。
  8. 8 个渲染阻塞 CSS 串在关键路径上（共 57 KB）。 桌面端它们几乎同时发起（669 ms），每个耗时 603–1154 ms 才完成， 把首次渲染推到 2664 ms；移动端在 Slow 4G 下单文件耗时 1.94–2.74 s。
    清单：entry.B1P0OSUR.css vendor-katex.Dn67XXJ1.css default.CTsR2ryP.css index.CaJfzrfq.css HomeWelcomeSection.Dnw1vJve.css ImageLoadingPlaceholder.BBEVY2Xd.css SearchBar.BnUd7MYy.css SideBar.DFxdOTzK.css。
    其中 vendor-katex.css（8 KB）属于文章公式渲染所需， 出现在与公式无关的首页首屏关键路径上完全没有必要； SideBar.css / SearchBar.css / ImageLoadingPlaceholder.css 分别是侧边栏、搜索框、图片占位这些非首屏或不关键部件的样式，同样被无条件阻塞加载。 8 个文件也意味着 8 次额外往返，合并 + 按需拆分是本项收益最大的改动。
  9. LCP 元素被推迟到 FCP 之后 2764 ms（桌面）/ 5668 ms（移动）才呈现。 LCP 元素是 DIV.hero-girl（面积 203877 px²）， 其底图 girl-full-silhouette.webp 只被 CSS 的 mask-image 引用， 浏览器在 CSS 解析完成前无法发现它：桌面端 1838 ms 才发起请求， 移动端 3461 ms。 该图为 mask 使用、只取 alpha 通道，体积本身仅 16 KB， 真正的问题是发现时机而非体积。
  10. 一个 58 KB 的「加载中」占位 GIF 出现在首屏资源里。 Picture/loading.gif 实测体积 58 KB， 桌面端耗时 1386 ms，移动端 5585 ms ——在 Slow 4G 上这是最慢的单个请求。占位图完全可以用内联 SVG / CSS 骨架屏替代， 属于"零成本砍掉的一块带宽"。另外它还被写进了 sitemap.xml 的 image:image（见附录）。
  11. JS 总量偏大，且大 chunk 被排到 CSS 之后才发起。 首页 JS 编码体积合计 573 KB，前三名： D2mlwmgT.js 227 KB、B1PWenEp.js 185 KB、BmQ9923M.js 78 KB。 最大 chunk 的请求时刻是 2026 ms（移动端 4074 ms）， 即 CSS 下载完之后——首屏 HTML 里没有对它们做 modulepreload， 白白浪费了 CSS 阻塞的那段时间。移动端每个大 chunk 下载 2.8–4.1 s。
  12. 客户端二次请求 /api/articles?summary=true&page=1&limit=100 落在 LCP 附近。 该请求 42 KB，桌面端 5257 ms 发出、耗时 1100 ms； 移动端 9904 ms 发出、耗时 1534 ms。 它是一个 SSG 站点上完全可以在构建期注入的数据请求，却发生在运行时， 并紧接着触发了移动端 t+9876 ms 的 UpdateLayoutTree 长任务（120 ms）。 桌面端 5428 ms 的 LCP 与它同处一段窗口，存在因果嫌疑。
  13. 两个第三方运行时依赖。 api.iconify.design（图标 JSON，731 ms）与 static.cloudflareinsights.com/beacon.min.js（1078 ms）。 前者是运行时跨域图标拉取，等于把首屏图标渲染绑在了第三方请求上； 后者虽小，但移动端解析执行占用了约 51 ms 主线程时间。
  14. 移动端主线程被样式/布局/绘制主导，TBT 达 1207 ms。 4 倍 CPU 降速 + Slow 4G 下，主线程忙 4480 ms （占 35.5%），共 8 个长任务， 最长 593 ms。而 JS 执行本身（V8 采样，仅统计 /_nuxt/ 下的代码） 约 877 ms，其余时间消耗在 Style(818.6 ms) / Layout(598.8 ms) / Paint(847.9 ms)。 这指向 CSS 选择器复杂度、DOM 规模（469 个节点）与图片解码， 而不是"JS 太慢"。
  15. 热缓存收益有限。 首页热缓存轮次的 FCP/LCP 与冷缓存基本同量级 （3160 / 5708 ms vs 2664 / 5428 ms）， 说明瓶颈不在回访缓存，而在首屏关键路径的编排本身。

六、优化建议（按优先级）

P0文章封面图改用按展示尺寸的变体（收益最大、改动最小）
为什么文章页 LCP 元素直接引用 /images/i_xxx，实测 302 → cfimg 上的 630 KB 原图，单请求耗时 —，导致 LCP 7340 ms、load 与之几乎同时。同一资源的 thumb 变体只有 49 KB（直出、无跳转），体积相差约 12.9 倍。
怎么做
  • 修 features/article-detail/components/CoverImage.vue：把 coverImageUrl || thumbnailUrl 改为优先 thumbnailUrl，或新增一个按容器实际宽度（桌面约 1160px、移动约 390px）生成的 hero 变体字段
  • 用 <img srcset/sizes> 提供多档位，让浏览器按 DPR 与视口选择，避免移动端下载桌面尺寸原图
  • 若必须使用原图，则至少让 /images/:id 直接 200 返回（去掉 302），省掉一次跨域 TLS 握手
怎么验证文章页封面请求编码体积 ≤100 KB、无 3xx 跳转；LCP ≤2500 ms（桌面），CLS 同步复测。
P0消除封面图容器比例在 onload 后被改写导致的布局位移
为什么CoverImage.vue 先以 aspect-ratio 1.5 渲染容器，图片 onload 后用 Math.max(imageRatio, 1.5) 改写容器比例，容器高度在图片到达后变化。轨迹中 t+7309 ms 的 0.00813 位移来源为 DIV/SPAN/BUTTON，与该时刻吻合；文章页 CLS 合计 0.0788（占比超过「良好」阈值 0.1 的一半以上）。
怎么做
  • 在构建期或 API 中提供封面图的 width/height（或宽高比），SSR 阶段就写出正确的 aspect-ratio 与 width/height 属性，而不是等 onload 再算
  • 若无法预知比例，则固定容器比例（不回写），用 object-fit: cover 裁切，避免高度变化
  • 对 t+6041 / 7557 / 9057 / 10608 ms 四处 sources: [] 的位移，用 DevTools Performance 面板开启 Layout Shift 区域逐个定位（水合期插入的区块、按钮、异步内容）
怎么验证文章页 CLS ≤0.1，且不再出现 onload 时刻的位移条目。
P0拆出首页关键路径上的非必需阻塞 CSS
为什么渲染阻塞样式共 8 个文件、57 KB，且包含首页根本用不到的 vendor-katex.css、侧边栏/搜索框样式。它们把 FCP 推到 2664 ms。
怎么做
  • 把 vendor-katex.css 从全局入口移除，改为在文章详情页按需引入（或 media="print" onload 的异步加载模式）
  • SideBar / SearchBar / ImageLoadingPlaceholder 等非首屏组件样式一并改为路由级或异步加载
  • 把首屏必需的样式合并为 1–2 个文件，减少往返次数
怎么验证重新采集首页 trace，确认 renderBlockingStatus=blocking 的请求数从 8 降到 ≤2，FCP 目标 ≤1800 ms。
P0让 LCP 底图提前可发现，并修正它的缓存策略
为什么girl-full-silhouette.webp 仅由 CSS mask 引用，浏览器要到 CSS 解析后才发起请求（桌面 1838 ms，移动 3461 ms）。LCP 比 FCP 晚 2764 ms（桌面）/ 5668 ms（移动）。该图响应头为 max-age=0, must-revalidate，是站内少数几个不享受长缓存的静态资源之一，恰好又是 LCP 底图。
怎么做
  • 在 <head> 中加 <link rel="preload" as="image" href="/hero/girl-full-silhouette.webp">
  • 或改为 <img> + fetchpriority="high" 参与 LCP 发现机制（同页普通 img 从发现到绘制只需数十 ms，而当前 mask 元素存在数秒空窗）
  • 为 /hero/** 与 /fonts/** 补上 Cache-Control: public, max-age=31536000, immutable（文件名带内容哈希或加版本参数），与 /_nuxt/* 保持一致
  • 确认它与 CSS 的 aspect-ratio: 1365/1617 约定保持一致，避免 mask 缩放位移
怎么验证LCP 元素开始时间应前移到 FCP 附近；LCP 目标 ≤2500 ms（桌面）/ ≤4000 ms（移动）；复测确认「加载完成 → 绘制」空窗是否随之消失。
P1替换 58 KB 的 loading.gif 占位图（同时修掉 sitemap 污染）
为什么首屏出现一个 58 KB 的 GIF 仅用于占位，移动端 Slow 4G 下单请求耗时超过 5 s；且它是首页第一个 LCP 候选（面积最大的一块绘制）。此外 sitemap.xml 的 312 条 image:loc 中有 74 条指向它，搜索引擎会把「加载中」动图当作页面配图。
怎么做
  • 改 shared/ui/ImageLoadingPlaceholder.vue：用内联 SVG 或纯 CSS 骨架屏替代 <img src="/Picture/loading.gif">（额外请求 0 字节）
  • 确保占位元素不参与 LCP 判定（避免大尺寸绘制），例如使用背景色/渐变而非大图
  • 在 sitemap 配置中排除占位图，或改为只用文章 thumbnailUrl 作为 image:loc
怎么验证首屏请求数 −1，移动端最慢资源排名中不再出现该文件；sitemap.xml 中不再出现 loading.gif。
P1把 /api/articles 的首屏数据挪到构建期
为什么SSG 站点在首屏运行时额外请求 42 KB 数据，并伴随一次长任务（移动端 t+9876 ms，120 ms）。
怎么做
  • 用 Nuxt 的 useAsyncData + prerender 产出静态 JSON，让首屏零运行时请求
  • 若非首屏所需，改为进入视口再加载（IntersectionObserver 懒加载）
怎么验证首屏不再出现 /api/articles 请求；该时刻附近的长任务消失。
P1为大 JS chunk 增加 preload 并检查拆分
为什么首页 JS 编码体积约 573 KB；最大的两个 chunk（232 KB / 190 KB）直到 CSS 下载完（2026 ms）才发起，HTML 中 modulepreload 数量为 0 —— 根因是 nuxt.config.ts 里 vitalizer 的 disablePreloadLinks: true。
怎么做
  • 对首屏必需 chunk 加 <link rel="modulepreload">，与 CSS 并行下载（可保留 vitalizer 对其它链接的处理）
  • 检查 232 KB chunk 是否可拆（例如把编辑器/KaTeX 等重依赖移出首屏 bundle）
  • 通过 build.rollupOptions.output.manualChunks 复核 vendor-katex / vendor-ui 的实际拆分结果
怎么验证大 chunk 的 startTime 前移到 CSS 请求同期；移动端 JS 下载窗口缩短。
P1降低移动端样式与布局成本
为什么移动端主线程 Style 818.6 ms / Layout 598.8 ms / Paint 847.9 ms，TBT 1207 ms，而 JS 执行不足 1 s。
怎么做
  • 检查卡片的阴影/圆角/滤镜与 mask 用法，避免大范围重绘
  • 图片统一 width/height + content-visibility: auto 减少首屏外的布局与解码
  • 避免在滚动/首屏阶段读取会强制同步布局的属性
怎么验证移动端 TBT 目标 ≤600 ms；Style/Layout/Paint 自耗时显著下降。
P2移除或延后运行时第三方依赖
为什么api.iconify.design 图标 JSON 与 cloudflareinsights beacon 都在关键窗口内。
怎么做
  • 图标改为构建期打包为本地 SVG sprite，去掉运行时跨域请求
  • 分析脚本改为 defer 且在 load 之后再注入
怎么验证首屏第三方请求数降为 0；跨域 RTT 从关键路径消失。
P2确认边缘节点与 HTML 压缩
为什么TTFB 稳定在 663–624 ms，且与设备无关。HTML 传输 59 KB / 解码 190 KB。
怎么做
  • 核对 Cloudflare 缓存规则：首页 HTML 是否走了边缘缓存而非每次都回源
  • 确认 Brotli 已开启（当前 HTML 压缩比约 0.31）
  • 若主要访客在中国大陆，评估就近加速方案对 TTFB 的影响
怎么验证重复测量 TTFB，目标 ≤800 ms。

附录 · 方法与原始数据

测量方法

  • 通过 Chrome DevTools Protocol 直连无头 Chromium，采集与 DevTools Performance 面板同源的 trace（分类含 devtools.timeline、blink.user_timing、disabled-by-default-v8.cpu_profiler、loading、v8 等），同时注入 PerformanceObserver 采集 LCP / CLS / longtask / event timing。
  • 主线程取 CrRendererMain；阶段自耗时由 trace 事件嵌套树计算（子事件递归扣除）；JS 热点来自 V8 CPU 采样落到渲染进程主 isolate。
  • 每轮使用全新的浏览器 profile 目录（冷缓存）；热缓存轮次复用上一轮 profile。
  • 事件数 140086，主线程 CrRendererMain（13196:29576），CPU 采样线程 13196:28256，采样总时长 7321 ms。

已知局限

  • 无头 Chromium 的合成器/GPU 路径与带界面 Chrome 存在差异，帧率类指标（如动画流畅度）不宜直接外推；LCP/FCP/CLS/TBT 类指标影响较小。
  • 每档条件为单次采样，未做多次取中位数，存在 ±10% 级别波动。
  • 移动端为模拟条件（4× CPU、Slow 4G），非真实设备。
  • 样本未包含交互指标 INP（本次未模拟真实交互）。

附带发现（非性能）

  • sitemap.xml 中首页的 image:image 第一条指向 /Picture/loading.gif。占位图不应作为内容图片进入站点地图，建议连同占位图改造一并移除。
  • 首页首屏客户端请求 /api/articles（详见关键发现第 6 条），对 SSG 站点而言属于可消除的运行时依赖。
